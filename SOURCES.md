## 1. SAP Procurement and Fuel Data

### Research Conducted

**Real-world SAP export formats investigated:**
- **SAP IDoc (Intermediate Document)**: XML-based, primarily for system-to-system integration
- **SAP BAPI (Business API)**: Function modules, requires SAP GUI or RFC connection
- **SAP OData Services**: RESTful APIs, modern but not always available
- **Flat File Exports (CSV/TXT)**: Most common for manual data extraction via transaction codes like MB51, ME2N

**Chose flat file CSV export because:**
- Most accessible to sustainability teams without IT support
- Transaction code MB51 (Material Documents) exports procurement/consumption data
- Realistic for initial client onboarding (before API access is provisioned)
- Can be generated by finance/procurement teams on-demand

### Real-World Format Characteristics

Typical SAP procurement exports contain:
- Material codes (10-18 digit alphanumeric)
- Material descriptions (in local language, sometimes German)
- Quantities with inconsistent units (L, GAL, KG, T, M3)
- Posting dates (multiple formats: DD.MM.YYYY, YYYY-MM-DD)
- Plant/location codes (alphanumeric facility identifiers)
- Document numbers (for traceability)

**Challenges in real SAP data:**
- Mixed languages (German headers: "Buchungsdatum", "Menge", "Werk")
- Inconsistent decimal separators (1.250,50 vs 1,250.50)
- Plant codes meaningless without master data lookup
- Material descriptions vary by plant/region

### Sample Data Structure

**File: `backend/sample_data/sample_sap_procurement.csv`**

```csv
Material,Material Description,Quantity,Unit,Posting Date,Plant
10001234,Diesel Fuel,1250,liter,2024-01-08,UK01
10001235,Petrol - Unleaded,850,liter,2024-01-15,UK01
```

**Design decisions:**
- English headers (most global companies use English SAP systems or translate exports)
- Simple plant codes (UK01, US02) representing facilities
- ISO date format (YYYY-MM-DD) for clarity in demo
- Realistic quantities: ~1000-2000 liters per fuel delivery
- Material codes: 8-digit (typical SAP range)

**What I simplified:**
- No document numbers (would clutter demo data)
- No movement types (101, 201, etc.)
- No storage locations or batch numbers
- Single currency/unit system
- English only (no German headers)

### What Would Break in Production

- **Master data dependency**: Material codes need lookup table (Material → Activity Type)
- **Multi-language**: Would need translation layer for German/French/Spanish headers
- **Unit ambiguity**: "KG" could be fuel or lubricant (different emission factors)
- **Historical data**: Years of backlog with evolving material codes
- **Plant code mapping**: Need facility address for location-based factors

## 2. Utility Electricity Data

### Research Conducted

**Real-world utility data sources investigated:**
- **Utility provider portals**: Most have CSV export (e.g., British Gas, EDF, National Grid)
- **PDF bills**: Common but require OCR/parsing (out of scope)
- **Smart meter APIs**: Modern but limited availability (UK: DCC, US: Green Button)
- **Interval data**: 15-min or hourly reads (very large datasets)

**Chose portal CSV export because:**
- Most common format for facilities teams
- Monthly aggregated data (not interval) is sufficient for carbon accounting
- PDF parsing adds complexity without demonstrating core logic
- Smart meter APIs not universally available

### Real-World Format Characteristics

Typical utility CSV exports contain:
- Meter ID/MPAN (Meter Point Administration Number in UK)
- Account number
- Reading dates (start/end of billing period)
- Previous and current readings
- Consumption (kWh, sometimes MWh for industrial)
- Charges (£/$/€ with currency and tax breakdown)
- Site name/address
- Sometimes: tariff type, peak/off-peak split

**Challenges in real utility data:**
- Billing periods don't align with calendar months
- Multiple meters per site (grid import, solar export, sub-meters)
- Units vary (kWh for small, MWh for large facilities)
- Estimated reads vs actual reads
- Different suppliers use different CSV formats

### Sample Data Structure

**File: `backend/sample_data/sample_utility_electricity.csv`**

```csv
Meter,Account Number,Bill Period,Reading Date,Previous Reading,Current Reading,kWh,Charges,Site,Country
MTR-GB-00142,ACC-2024-8801,2024-01,2024-01-31,48320,54180,5860,£877.42,Head Office - London,GB
MTR-GB-00287,ACC-2024-9145,2024-01,2024-01-31,112450,124380,11930,£1787.06,Manchester Warehouse,GB
```

**Design decisions:**
- Meter IDs in realistic format (MTR-{COUNTRY}-{NUMBER})
- Bill Period as YYYY-MM (month granularity)
- Both readings and calculated kWh (as utilities provide both)
- Charges in local currency (£) for realism but not used in calculations
- Site names descriptive (office/warehouse/factory)
- Country code for regional emission factor lookup

**Realistic quantities:**
- Office (5-6 MWh/month): ~200 kWh/day
- Warehouse (10-12 MWh/month): ~400 kWh/day with lighting/HVAC
- Factory (13-16 MWh/month): ~500 kWh/day with machinery

**What I simplified:**
- No peak/off-peak split (time-of-use tariffs)
- No demand charges (kW vs kWh)
- No solar generation/export
- Single meter per site (real sites have 5-20 meters)
- All actual reads (no estimated)

### What Would Break in Production

- **Multi-meter sites**: Need aggregation logic (sum? average?)
- **Estimated reads**: Should be flagged lower quality
- **Solar**: Need separate handling (grid import vs total consumption)
- **Time-of-use**: Peak hours have different emission factors (time-based grid carbon intensity)
- **Supplier switching**: Historical data from multiple suppliers with different formats
- **Sub-metering**: Tenant vs landlord responsibility in shared buildings

## 3. Corporate Travel Data

### Research Conducted

**Real-world travel platforms investigated:**
- **Concur (SAP)**: XML or CSV exports, extensive API
- **Navan (formerly TripActions)**: REST API with webhooks
- **Egencia**: CSV exports via admin portal
- **Manual spreadsheets**: Common for small companies

**Chose CSV export (Concur-style) because:**
- API integration out of scope (see TRADEOFFS.md)
- CSV format is what sustainability teams receive from travel managers
- Demonstrates the calculation logic (same whether from API or file)

### Real-World Format Characteristics

Typical travel data contains:
- Trip dates (departure, return)
- Employee ID/name
- Origin and destination (airport codes or city names)
- Distance (if provided; often must be calculated)
- Mode (flight, rail, car rental, taxi)
- Class (economy, business, first for flights)
- Cost (for spend-based fallback if activity data missing)
- Booking reference

**Challenges in real travel data:**
- Airport codes vs city names (need geocoding: "London" → LHR/LGW/STN/LCY?)
- Missing distances (must calculate from airport codes)
- Multi-leg trips (London → Dubai → Singapore = 2 flights)
- Rail: high-speed vs regional (different factors)
- Car rental: vehicle type affects emissions (sedan vs SUV)

### Sample Data Structure

**File: `backend/sample_data/sample_corporate_travel_simple.csv`**

```csv
Date,Employee,From,To,Distance,Mode,Flight Class
2025-03-04,Alice Johnson,London,New York,5570,flight,economy
2025-03-10,Bob Chen,London,Paris,456,rail,
2025-03-15,Alice Johnson,New York,San Francisco,4130,flight,business
2025-03-18,Carol Davis,Chicago,Milwaukee,148,car,
2025-03-22,Bob Chen,Paris,Amsterdam,430,rail,
```

**Design decisions:**
- Simple departure date (return date not needed for emissions calculation)
- Employee names (demonstrates multi-user travel data)
- Locations as city names (realistic; geocoding would be a production concern)
- Distance pre-calculated in km (avoids airport code lookup in demo)
- Mode as plain text (flight/rail/car) — parsed and classified by normalization service
- Flight Class as optional column (blank for non-flight modes)

**Haul classification (DEFRA 2024 threshold):**
- Short haul: < 3,700 km — generates `flight_economy_short_haul` activity type
- Long haul: ≥ 3,700 km — generates `flight_economy_long_haul` activity type

**Emission factors seeded (from DEFRA 2024):**
- `flight_economy_short_haul`: 0.158 kg CO2e/km
- `flight_economy_long_haul`: 0.103 kg CO2e/km
- `flight_business_short_haul`: 0.237 kg CO2e/km
- `flight_business_long_haul`: 0.309 kg CO2e/km
- `travel_rail`: 0.041 kg CO2e/km
- `travel_car`: 0.171 kg CO2e/km
- `travel_bus`: 0.097 kg CO2e/km

**What I simplified:**
- Pre-calculated distances (no airport code → lat/long → great circle distance)
- No radiative forcing multiplier (aviation has ~1.9× non-CO2 effects from contrails, NOx)
- No WTT (well-to-tank) emissions separate from combustion
- Single flight class per trip (no mixed-class itineraries)
- No hotel stays (Scope 3 Category 1, not Category 6)

### What Would Break in Production

- **Airport code ambiguity**: "Paris" → CDG or ORY or BVA?
- **Multi-leg trips**: Need to parse full itineraries (LHR → DXB → SIN)
- **Radiative forcing**: Aviation non-CO2 effects are significant and increasingly required in disclosure
- **Class upgrades**: Passenger books economy, gets upgraded to business at the gate
- **Private jets**: Require per-aircraft factors (no per-seat allocation)
- **Rail electrification**: UK rail is partially electric (0.041 kg/km) vs diesel-only regional lines (higher)
- **Ground transport**: Taxi/rideshare distances are rarely recorded; spend-based estimation needed

## Cross-Cutting Research Insights

### Emission Factor Sources

**Primary source: UK DEFRA 2024 Greenhouse Gas Reporting Conversion Factors**
- Published annually by the UK Department for Environment, Food and Rural Affairs
- Covers fuels, electricity (by country), refrigerants, travel, waste, and water
- Freely available, no license required
- Widely accepted by auditors and used in mandatory UK Streamlined Energy and Carbon Reporting (SECR)

**Additional sources used:**
- **US EPA eGRID 2024**: US electricity grid emission factor (0.386 kg CO2e/kWh)
- **IEA World Energy Outlook 2024**: Global average electricity factor (0.475 kg CO2e/kWh) as GLOBAL fallback

**Alternative sources considered and not used:**
- **IPCC AR6 guidelines**: Academic precision, not formatted for practical carbon accounting
- **ecoinvent database**: Highly detailed lifecycle factors, but requires a paid license
- **GHG Protocol cross-sector tools**: Good for specific sectors, but DEFRA is more comprehensive for the mix of source types here

### Data Quality in the Real World

Key patterns observed from public sustainability reporting case studies and practitioner forums:

- Roughly 20–30% of records in a first upload contain missing or incorrect fields
- Facilities teams report in the units their suppliers use (kWh, gallons, therms) — not in CO2e terms
- Manual data entry in spreadsheets introduces typos in plant codes, dates, and quantities
- Units are rarely consistent within the same company across sites or years
- Historical data quality degrades: records from 3+ years ago often have gaps that were acceptable at the time but now matter for baseline reporting

**Implemented in response to this:**
- Data quality scoring (HIGH/MEDIUM/LOW) with a penalty-based algorithm
- `QualityService` with five automated checks: date validity, missing emission factors, location completeness, statistical anomaly detection (3× average threshold), and duplicate detection (±5% quantity, ±1 day)
- Unit normalization to a canonical unit per source type before factor application
- Review workflow so analysts can correct issues before records are approved

## Summary

Each sample file was designed based on:
1. Research into real-world export formats from SAP, utility portals, and corporate travel platforms
2. Examination of public documentation (SAP Community, Concur developer docs, utility provider help pages, DEFRA guidance)
3. Trade-offs between realism and demo clarity — enough detail to demonstrate the parsing and normalization logic, not so much complexity that the pipeline becomes the story

The sample data demonstrates:
- Parsing realistic column structures with optional fields
- Handling unit variation (the normalization service is exercised even in the demo)
- Applying emission factors correctly by activity type, haul length, and class
- Generating the data quality issues that the `QualityService` is designed to catch

Simplified enough to:
- Keep the 4-day prototype focused on data model and calculation accuracy
- Allow any evaluator to upload the files and see real results immediately
- Show judgment about what is essential vs what is future scope
